## 2. 環境の全体像

| 環境 | 用途 | DB | Webサーバー | 起動方法 |
|---|---|---|---|---|
| ローカルPC | 開発・動作確認 | SQLite（既定） | Django開発サーバー | `dev-setup.ps1` / `manage.py runserver` |
| 研究室サーバー | 本番運用 | PostgreSQL 16 | nginx + gunicorn | `docker compose up -d` |

設定は環境変数で切り替える。設定ファイルは環境ごとに分離しており、いずれも git 管理外。

| ファイル | 用途 | 読み込み方 |
|---|---|---|
| `.env.example` | 雛形（git管理対象） | — |
| `.env` | ローカル開発用 | `config/settings.py` が起動時に読み込む |
| `.env.docker` | Docker Compose 用 | `docker-compose.yml` の `env_file` |

主要な環境変数は次のとおり。

| 変数 | ローカル | 本番 | 説明 |
|---|---|---|---|
| `DJANGO_SECRET_KEY` | 任意 | **要変更** | セッション・CSRFの署名鍵 |
| `DJANGO_DEBUG` | `1` | `0` | `1` のときエラー詳細を表示。本番では必ず `0` |
| `DJANGO_ALLOWED_HOSTS` | `localhost,127.0.0.1` | サーバーのホスト名 | 許可するHostヘッダ |
| `DJANGO_CSRF_TRUSTED_ORIGINS` | `http://127.0.0.1:8000` | `http://<ホスト名>` | POST時のOrigin検証 |
| `USE_SQLITE` | `1` | `0` | `1` でSQLite、`0` でPostgreSQL |
| `POSTGRES_*` | 未使用 | 要設定 | DB名・ユーザー・パスワード・ホスト・ポート |

## 3. ローカルPCでの起動

### 3.1 前提

- Python 3.11 以上（`python --version` で確認）
- Docker は不要（SQLiteで動作する）

### 3.2 一括セットアップ（推奨）

リポジトリのルートで PowerShell から次を実行する。仮想環境作成・依存パッケージ導入・
`.env` 生成・マイグレーション・デモデータ投入・開発サーバー起動をまとめて行う。

```powershell
.\dev-setup.ps1 -Run
```

`-Run` を付けない場合はセットアップのみ行い、起動コマンドを表示して終了する。
2回目以降の実行も安全（マイグレーション・デモデータはいずれも冪等）。

起動後、ブラウザで <http://127.0.0.1:8000/> を開く。

### 3.3 個別手順（スクリプトを使わない場合）

```powershell
python -m venv .venv
```

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
```

```powershell
Copy-Item .env.example .env
```

`.env` を編集し、ローカル用に次の2点を設定する。

```
DJANGO_DEBUG=1
USE_SQLITE=1
```

```powershell
.\.venv\Scripts\python.exe manage.py migrate
```

```powershell
.\.venv\Scripts\python.exe manage.py runserver
```

ポートを変える場合は `manage.py runserver 8080` のように指定する。

### 3.4 ログインアカウント

サインアップ画面は設けていない。アカウントは管理者が発行する。

#### (a) 管理者アカウントを作成する

最初のアカウントは CLI から作成する。対話的にメールアドレス・表示名・パスワードを入力する
（パスワードは画面に表示されない）。

```powershell
.\.venv\Scripts\python.exe manage.py createsuperuser
```

作成されるユーザーの属性は次のとおり。

| 項目 | 値 |
|---|---|
| ログインID | 入力したメールアドレス |
| ロール | 教員（faculty） |
| `is_staff` / `is_superuser` | いずれも True（管理画面を利用可） |

作成後 <http://127.0.0.1:8000/login> からログインでき、`/admin/` では全モデル
（優先度②〜④のテーブルを含む）を直接操作できる。研究室メンバーのアカウントは
`/admin/` の「ユーザー」から追加する。

> **ロールと管理権限は別物**：`is_superuser` は管理画面の権限、`role` はアプリ内の権限を決める。
> `/admin/` から追加したユーザーはロールの既定が学生になる。基本設計書4章のとおり
> 承認操作（サーバー長期利用申請・出張費申請）は**教員ロール限定**のため、
> 学生ロールのまま管理者権限を付けても承認画面は使えない（`/admin/` からの直接編集は可能）。
> 優先度③④を実装する際に、承認権限の判定をロールで見るままとするかを確認する必要がある。

#### (b) デモデータのアカウント（動作確認向け）

```powershell
.\.venv\Scripts\python.exe manage.py seed_demo
```

| メールアドレス | パスワード | ロール |
|---|---|---|
| `student@example.local` | `demo-pass-12345` | 学生 |
| `teacher@example.local` | `demo-pass-12345` | 教員（`/admin/` 利用可） |

投入されるデモデータは、研究日記3件・予定4件（学会紐付け・研究室共通を含む）・
学会準備1件（チェックリスト5項目、締切は実行日から10日後）。データは `student@example.local` に
紐づくため、画面の中身を確認するときはこのアカウントでログインする。
作り直す場合は `manage.py seed_demo --reset` を使う。

`seed_demo` は `DJANGO_DEBUG=1` のときだけ動作し、本番環境では実行を拒否する。

### 3.5 パスワードの設定・変更

**画面上のパスワード変更・再設定機能は未実装。** 実装しているのは `/login` と `/logout` のみで、
詳細設計書4章のエンドポイント一覧にもパスワード関連の画面は含まれていない。
現状は次の2つの手段で変更する。

| 手段 | 方法 | 対象 |
|---|---|---|
| 管理画面 | `/admin/` → ユーザー → 対象ユーザー → パスワード欄のリンクから変更 | 管理者が他人のパスワードもリセットできる |
| CLI | `manage.py changepassword <メールアドレス>` | サーバーにログインできる人 |

将来的に追加する場合の選択肢は次の2段階。

| | 内容 | 前提 |
|---|---|---|
| A. パスワード変更画面 | ログイン中の本人が変更（Django標準の `PasswordChangeView`） | なし |
| B. パスワード再設定 | 「パスワードを忘れた方」からメール経由で再設定（`PasswordResetView` 一式） | SMTP設定（`EMAIL_*`）が必要。現在は未設定 |

### 3.6 停止

開発サーバーを起動したコンソールで `Ctrl + C` を押す。
別プロセスとして起動した場合は次のコマンドで停止できる。

```powershell
Get-CimInstance Win32_Process -Filter "Name='python.exe'" | Where-Object { $_.CommandLine -like '*runserver*' } | ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```

### 3.7 ローカルでPostgreSQLを使う場合

本番と同じDBで確認したい場合は、PostgreSQL を用意して `.env` を次のように変更する。

```
USE_SQLITE=0
POSTGRES_HOST=127.0.0.1
POSTGRES_PORT=5432
POSTGRES_DB=selapo
POSTGRES_USER=selapo
POSTGRES_PASSWORD=<設定した値>
```

変更後に `manage.py migrate` を再実行する（SQLiteのデータは引き継がれない）。

## 4. 研究室サーバーでの起動（Docker Compose）

### 4.1 前提

- Docker Engine と Docker Compose v2 が動作していること
- 80番ポートが空いていること
- 公開範囲は学内ネットワークに限定する（要件定義書 5章）。外部公開する場合は前段のFWで制御する

### 4.2 構成

`docker-compose.yml` は3サービスで構成される。

| サービス | イメージ | 役割 |
|---|---|---|
| `db` | postgres:16-alpine | データベース。データは `pgdata` ボリュームに永続化 |
| `web` | 本リポジトリの Dockerfile | Django + gunicorn（3ワーカー） |
| `nginx` | nginx:1.27-alpine | 80番で受け、静的ファイルを直配信、それ以外を `web` へ中継 |

### 4.3 手順

**手順1: 設定ファイルを作成する**

```bash
cp .env.example .env.docker
```

`.env.docker` で次を必ず設定する。

- `DJANGO_SECRET_KEY`：ランダムな長い文字列に変更する
- `DJANGO_DEBUG=0`
- `USE_SQLITE=0`
- `DJANGO_ALLOWED_HOSTS`：サーバーのホスト名（例 `selapo.example.ac.jp`）
- `DJANGO_CSRF_TRUSTED_ORIGINS`：`http://selapo.example.ac.jp`
- `POSTGRES_PASSWORD`：推測されない値に変更する

`SECRET_KEY` は次のコマンドで生成できる。

```bash
python -c "from secrets import token_urlsafe; print(token_urlsafe(50))"
```

**手順2: 起動する**

```bash
docker compose up -d --build
```

`web` コンテナの起動時に `migrate`（DBスキーマ適用）と `collectstatic`（静的ファイル収集）が
自動実行される。`db` のヘルスチェック通過を待ってから `web` が起動する。

**手順3: 管理ユーザーを作成する（初回のみ）**

```bash
docker compose exec web python manage.py createsuperuser
```

**手順4: 動作確認**

`http://<サーバーのホスト名>/` を開き、ログイン画面が表示されることを確認する。
続いて管理画面 `http://<サーバーのホスト名>/admin/` にログインし、研究室メンバーのアカウントを発行する。

### 4.4 運用コマンド

| 目的 | コマンド |
|---|---|
| 状態確認 | `docker compose ps` |
| ログ確認 | `docker compose logs -f web` |
| 停止 | `docker compose down` |
| 停止（DBも削除） | `docker compose down -v` ※**データが消える** |
| 再起動 | `docker compose restart web` |
| コード更新の反映 | `git pull && docker compose up -d --build` |
| マイグレーション手動実行 | `docker compose exec web python manage.py migrate` |
| DBバックアップ | `docker compose exec db pg_dump -U selapo selapo > backup.sql` |

## 6. トラブルシューティング

| 症状 | 原因と対処 |
|---|---|
| `.\dev-setup.ps1` が「このシステムではスクリプトの実行が無効」で止まる | 実行ポリシーの制限。`Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass` を実行してから再試行する |
| `Error: That port is already in use.` | 8000番が使用中。`manage.py runserver 8001` で別ポートを使うか、3.6の手順で既存プロセスを停止する |
| `django.db.utils.OperationalError: could not connect to server` | `USE_SQLITE=0` なのにPostgreSQLへ接続できていない。ローカルなら `.env` で `USE_SQLITE=1` に戻す。Dockerなら `docker compose ps` で `db` の状態を確認する |
| 画面のデザインが崩れる（枠線だけの表示になる） | Bootstrap/htmx をCDNから取得できていない。学内ネットワークが外部へ出られない場合は、両ファイルを `static/` 配下に置き `templates/base.html` の参照を `{% static %}` に差し替える |
| ログインしても弾かれる／CSRF エラーになる | `DJANGO_ALLOWED_HOSTS` と `DJANGO_CSRF_TRUSTED_ORIGINS` に実際のアクセス元URLが含まれているか確認する |
| パスワードを忘れた／作成直後でログインできない | 画面上の再設定機能は未実装（3.5参照）。`manage.py changepassword <メールアドレス>` か、他の管理者が `/admin/` から再設定する |
| `manage.py seed_demo` が `CommandError` で止まる | 仕様どおりの挙動。`DJANGO_DEBUG=1` の環境でのみ実行できる |
| `.ps1` を編集したら構文エラーになった | Windows PowerShell 5.1 はBOMなしUTF-8を誤読する。UTF-8（BOM付き）で保存する |
| 本番で静的ファイルが404になる | `collectstatic` が未実行。`docker compose exec web python manage.py collectstatic --noinput` を実行する |

## 7. 補足

- **優先度②以降の機能**：モデル定義とマイグレーションは完了しているが専用画面は未実装。
  管理画面 `/admin/` から登録・参照できる。
- **認証方式**：メールアドレス＋パスワードのDjango標準認証（詳細設計書 3.1）。
  将来の学内SSO移行時は `AUTHENTICATION_BACKENDS` の差し替えのみで対応できる構成としている。
- **サーバー利用状況の収集（詳細設計書 3.4）**：収集バッチは未実装。実装時に
  取得方式（SSH／監視エージェント／手動報告）を確定させる必要がある。
