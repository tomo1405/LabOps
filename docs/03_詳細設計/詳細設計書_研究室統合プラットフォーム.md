## 3. 主要処理フロー

### 3.1 ログイン・認証フロー

1. 利用者がログイン画面でメールアドレス／パスワードを入力
2. Djangoの認証バックエンドが照合し、セッションを発行
3. ロール（教員／学生）に応じて表示メニュー・操作可能範囲を出し分け
4. ※将来的にSSO移行する場合は、この認証バックエンド部分のみを差し替える設計とする（画面・他モジュールへの影響を最小化）

### 3.2 サーバー長期利用申請の承認フロー

1. 学生／教員が申請フォームからサーバー・利用期間・理由を入力し申請（status=pending）
2. 教員ロールのユーザーに申請一覧が表示される
3. 教員が承認／却下を選択（reviewed_by, reviewed_at, statusを更新）
4. 申請者に結果が画面上の通知欄・一覧のステータス表示で伝わる

### 3.3 出張費申請の承認フロー

1. 申請者が出張先・目的・金額・期間を入力し申請（status=pending）
2. 教員が申請一覧から内容を確認し承認／却下
3. 承認後のステータスは一覧で確認できる（経理への提出等、システム外の手続きは対象外）

### 3.4 サーバー利用状況データ収集フロー（バッチ）

1. 研究室サーバー・学科サーバーそれぞれで、定期実行タスク（cron等）がリソース使用率を取得
2. 取得したデータをServerUsageSnapshotとしてDBに保存
3. ダッシュボード画面がAPI経由で直近のデータを取得しグラフ表示（Chart.js）
4. データ取得元（SSH経由でのログ収集／監視エージェント／手動報告）は、実装時にサーバーへのアクセス権限に応じて選定する

### 3.5 学会準備・締切管理フロー

1. ユーザーが学会名・締切日・チェックリスト項目を登録
2. チェックリストの各項目をhtmx経由でチェックON/OFF
3. 締切が近づいた項目はダッシュボードで強調表示（バッチ or 画面表示時の日付比較で判定）

### 3.6 チケット（開発リクエスト）のライフサイクル

1. 誰でも新規チケットを起票（status=open）
2. 対応者（主に開発者本人）がstatusをin_progressに変更
3. コメントで進捗ややり取りを記録
4. 完了したらstatus=doneに変更し一覧から可視化

### 3.7 研究室HP Newsの公開フロー

1. 教員／学生がNews記事を下書き作成（status=draft）
2. 内容確定後に公開操作（status=published, published_atを記録）
3. 公開済み記事のみ研究室HP側の表示対象とする（HP側との連携方式は既存HPの技術構成に応じて実装時に決定）

## 5. 実装工程への申し送り事項

- テーブル定義（2章）をそのままDjangoモデルへ落とし込むことを想定
- htmxを使う箇所（在室状態切替、チェックリスト、チケットステータス変更）は部分レンダリング用のテンプレート断片を別途用意する
- サーバー利用状況データ収集（3.4）は、実装時にサーバーへのアクセス方式（SSH／監視エージェント／手動）を確定させる必要がある
- 優先実装順は基本設計書に準拠：①研究支援系 → ②情報共有・コミュニケーション系 → ③サーバー利用状況・申請系 → ④事務・その他
