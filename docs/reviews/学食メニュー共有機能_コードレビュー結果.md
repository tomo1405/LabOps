## 3. 指摘事項

### REV-CAN-001：メニュー本体と品目の置換が原子的でなく、失敗・同時更新でデータを失う

- 重要度：**P1（重大）**
- 分類：データ整合性、トランザクション、競合状態
- 該当箇所：
  - `community/views.py:185-197`
  - `community/views.py:214-225`
  - `community/views.py:236-249`

#### 内容

`_save_menu_items()` は既存品目をすべて削除してから `bulk_create()` するが、この処理とメニュー本体の作成・更新は `transaction.atomic()` でまとめられていない。品目挿入が失敗すると、メニュー本体の更新と既存品目の削除だけが確定する部分更新になる。

編集で日付を既存の別日に変更する処理も、置換先の `CanteenMenu` を削除してから元のメニューを保存する。後続の `menu.save()` または品目保存が失敗した場合、置換先のメニューとその品目を失ったままになる。

さらに、同じ日付へ複数のリクエストが並行すると、`update_or_create()` から品目置換までの全体をロックしていないため、削除と挿入が交差して、最後の入力だけでなく双方の品目が混在する可能性がある。「登録・編集のたびに、その日の品目を入力内容で置き換える」という仕様を満たさない。

#### 再現結果

既存品目 `old` を持つメニューに対し、`bulk_create()` だけを意図的に失敗させて `_save_menu_items()` を実行したところ、`RuntimeError` 後の品目一覧が空 (`items_after_failure=[]`) になった。確認用データは外側のトランザクションでロールバックしており、作業DBには残していない。

#### 影響

- 一時的なDB障害や保存エラーで、利用者には500応答が返る一方、既存のメニュー内容は一部または全部失われる。
- 日付変更時は、編集中のメニューだけでなく置換先の日付の登録も失い得る。
- 同時登録の結果が「最後の入力による置換」にならず、異なる投稿の品目が混在し得る。

#### 推奨修正

- 作成・更新、置換先の削除、既存品目の削除、新品目の挿入を1つの `transaction.atomic()` で囲む。
- 対象日付の既存メニューを `select_for_update()` でロックし、同日への作成・再登録・日付移動を直列化する。
- 新規日付への同時作成で一意制約競合が起きる場合も、トランザクション内で再取得して定義した上書き処理へ収束させる。

#### 追加すべきテスト

- 品目挿入が失敗した場合、メニュー本体、登録者、既存品目、置換先メニューがすべて変更前へロールバックされる。
- 同日への同時再登録後、品目が片方の入力一式だけになり、混在・重複・欠落しない。
- 未登録日の同時作成、および異なるメニューを同じ日へ移動する同時編集でも、日付の一意性と置換仕様を保つ。

#### 対応（2026-09-06）

**対応済み**

- メニューの保存を新規モジュール `community/canteen.py` に集約し、
  `save_menu(form, user, menu=None)` を唯一の入口にした。
  `@transaction.atomic` により、置換先の削除・本体の作成／更新・既存品目の削除・
  新品目の挿入がすべて1つのトランザクションで確定する。
- `_lock_menu()` で対象日付の既存メニューを `select_for_update()` によりロックしてから触る。
  同じ日への登録・再登録・日付移動が直列化される。
- 未登録日への同時作成は `_get_or_create_locked()` で扱う。
  一意制約違反になった場合はロック付きで読み直し、定義どおりの上書き処理へ合流させる。
- ビューの `_save_menu_items()` と `update_or_create()`、
  編集時の「置換先を先に削除してから保存」する処理は削除し、実装をサービスへ一本化した。
  `canteen_create` / `canteen_update` はどちらも `save_menu()` を呼ぶだけになる。

補足：`select_for_update()` は SQLite では無視される（Django の仕様）。
本番のPostgreSQLでのみ実際の行ロックが効くため、テストはロックの発行・
トランザクション境界・一意制約競合時の合流を検証する形にしている（7.5節参照）。

### REV-CAN-002：品名の100文字制約をフォームで検証せず、DB保存時に失敗する

- 重要度：**P2（中）**
- 分類：入力検証、エラーハンドリング、環境差
- 該当箇所：
  - `community/forms.py:15-27`
  - `community/forms.py:58-66`
  - `community/models.py:232-234`
  - `community/views.py:188-196`

#### 内容

品名は `CanteenMenuItem.name` で `max_length=100` と定義されているが、画面入力にはモデルフィールドではなく独立した `set_meals` / `donburi` の `CharField` を使っている。各行を分割した後に長さを検証せず、`bulk_create()` はモデルの `full_clean()` も呼ばない。

101文字の1行を `set_meals` に渡した再現確認では、`CanteenMenuForm.is_valid()` が `True` となり、101文字の品名が保存処理へ渡った。SQLiteは `varchar(100)` の長さを強制しないため開発・テストでは保存できるが、本番のPostgreSQLでは長さ超過として保存時エラーになる可能性がある。

#### 影響

- ログインユーザーが長い品名を送ると、本番環境だけ500応答になる可能性がある。
- メニュー本体を先に更新する現状では、REV-CAN-001と組み合わさり既存品目の消失にもつながる。
- SQLite上のテスト成功だけでは本番DBとの動作差を検出できない。

#### 推奨修正

- フォームの `clean_set_meals()` / `clean_donburi()` または共通検証で、空行除去後の各品名が100文字以内かを検証し、該当行を示すフォームエラーを返す。
- 制約値を重複定義せず、`CanteenMenuItem._meta.get_field("name").max_length` などモデル定義を参照する。
- 必要に応じて品目数や入力全体の上限も定義し、過大入力をフォーム段階で拒否する。

#### 追加すべきテスト

- 定食・丼の各欄で100文字は受理し、101文字は400応答とフォームエラーになる。
- 複数行のうち1行だけが超過した場合も、既存メニューが変更されない。
- 本番相当のPostgreSQLを使う統合テストでも、長さ超過が500応答にならない。

#### 対応（2026-09-06）

**対応済み（PostgreSQL統合テストのみ未実施）**

- `CanteenMenuForm` に `clean_set_meals()` / `clean_donburi()` を追加し、
  空行を除いた各品名の長さを検証するようにした。
  違反した場合は該当行を挙げたフォームエラーを返す
  （例: 「2行目、3行目が長すぎます。1品は100文字以内にしてください。」）。
- 制約値は `CanteenMenuForm.ITEM_MAX_LENGTH` としてモデルの
  `CanteenMenuItem.name` の `max_length` を参照し、二重定義を避けた。
- 「必要に応じて品目数の上限も定義する」という指摘に対して、
  1区分あたり `MAX_ITEMS = 50` 品の上限を設けた。どちらの値も入力欄のヘルプテキストに表示する。
- `set_meal_names()` / `donburi_names()` は検証済みのリストを返すだけに変更し、
  検証を通らない値が保存処理へ渡らないようにした。
- 品名エラーが出ているときは「定食・アラカルト丼・補足のいずれかを入力してください」を
  重ねて出さないようにした（エラーの原因が分かりにくくなるため）。
- 本番相当のPostgreSQLを使う統合テストは**未実施**（7.5節参照）。
  ただし長さ超過はフォーム段階で400応答になるため、DBまで到達しない。

## 4. 良好だった点

- 閲覧・登録・編集・削除はログインを必須とし、更新系操作はPOSTとDjangoのCSRF保護を利用している。削除はGETで実行せず確認画面を表示する。
- `CanteenMenu.date` の一意制約により日付ごとの1件をDBでも保証し、同日再登録と既存日への移動を上書きとして扱っている。
- 定食とアラカルト丼を別レコードで保持し、`position` と安定した並び順で入力順を再現している。空行を除去し、全欄空だけを拒否する一方、臨時休業など補足だけの登録を許可している。
- テンプレート出力はDjangoの自動エスケープを維持しており、品名・補足・登録者名をHTMLとして直接解釈しない。
- 登録者は最終更新者へ更新され、ユーザー削除時は `SET_NULL` で献立を保持して「登録者不明」と表示する。共有情報として全メンバーが編集・削除できる仕様とも整合する。
- 一覧取得では登録者を `select_related()`、品目を `prefetch_related()` し、今日と直近7件の表示時にN+1クエリを避けている。
- 品目の区分・順序・空行・再登録・編集・削除・履歴・ダッシュボード・登録者更新／削除に関するテストが用意されている。
