## 3. 指摘事項

### REV-SCH-001：共通予定を別ユーザーが編集すると関連情報が失われる

- 重要度：**P1（重大）**
- 分類：データ整合性、フォームの選択肢制御
- 該当箇所：
  - `research/forms.py:107-121`
  - `research/views.py:526-535`

#### 内容

`ScheduleEventForm` は、関連する学会準備の候補を現在の操作ユーザー本人のデータに限定し、参加者候補からも現在の操作ユーザーを除外している。この制御は個人予定の作成・編集には適しているが、全メンバーが編集できる共通予定にも同じフォームが使用されている。

例えば、ユーザーAが「Aの学会準備」と「参加者B」を設定した共通予定を作成し、その予定をユーザーBが編集すると、次の状態になる。

- Aの学会準備がBのフォーム候補に含まれないため、画面上で既存の選択を維持できない。
- B自身が参加者候補から除外されるため、既存の参加者Bを維持できない。
- 画面の表示どおりに保存すると、学会準備との紐付けや参加者Bが予定から削除される。
- 元のIDを直接POSTして維持しようとすると、フォームのqueryset外であるため「有効な選択肢ではありません」として拒否される。

共通予定は全メンバーが編集可能という仕様のため、これは通常の操作経路で発生する。

#### 影響

- タイトルなど別の項目だけを変更した場合でも、無関係な関連情報が失われる。
- 画面上で既存値が表示されないため、利用者は保存前にデータ消失へ気付きにくい。
- 共通予定の編集者によって保存結果が変わり、データの一貫性が保てない。

#### 推奨修正

- 編集時は、現在ユーザー向けの通常候補に加えて、インスタンスに設定済みの学会準備と参加者をquerysetへ含める。
- または、共通予定に学会準備を関連付ける際の所有権ルールを明確化し、そのルールに合わない編集では既存値を変更せず維持する。
- 参加者については「現在の編集者」ではなく、予定の担当者を候補除外の基準にする。担当者のない共通予定で誰を候補から除外するかも仕様として明示する。

#### 追加すべきテスト

- 別ユーザーが共通予定のタイトルだけを変更しても、作成者の学会準備との紐付けが維持される。
- 別ユーザーが共通予定を保存しても、そのユーザー自身を含む既存参加者が維持される。
- 共通予定の編集フォームに既存の学会準備と参加者が表示される。
- 無関係な他ユーザーの学会準備を新規選択できない。

### REV-SCH-002：htmxの入力エラー応答でフィールド別エラーが表示されない

- 重要度：**P2（中）**
- 分類：入力検証、エラー表示、操作性
- 該当箇所：
  - `templates/research/schedule.html:18-25`
  - `templates/research/partials/schedule_calendar.html:20-23`
  - `templates/research/partials/schedule_form_fields.html:2-20`
  - `research/views.py:511-513`

#### 内容

予定追加フォームは、htmxの差し替え対象として `#schedule-calendar` を指定している。しかし、フィールド別のエラーを描画する追加フォームはこの要素の外側にある。

バリデーション失敗時、サーバーはエラー付きフォームをコンテキストへ設定するものの、返却する `schedule_calendar.html` には汎用メッセージ「入力内容を確認してください。」しか含まれない。このため、例えば終了日時が開始日時より前でも、具体的にどの項目が不正なのか画面へ反映されない。

また、成功時も追加フォーム自体は差し替えられないため、送信済みの入力値が残り、同じ予定を再送信しやすい。

#### 影響

- 利用者が入力の修正箇所を判断できない。
- 仕様書に記載された「入力内容を保持したままエラーメッセージを表示する」を十分に満たさない。
- 成功後の入力値残留によって予定を重複登録する可能性がある。

#### 推奨修正

- カレンダーと追加フォームを包含する要素を差し替え対象にし、エラー付きフォームまたは初期化済みフォームを応答へ含める。
- あるいは、htmxのOut-of-Band Swapを利用し、カレンダーとフォームを個別に更新する。
- 成功時はフォームを初期化し、失敗時は入力値とフィールド別エラーを維持する。

#### 追加すべきテスト

- 終了日時が開始日時より前の場合、HTTP 400応答本文に具体的なフィールドエラーが含まれる。
- バリデーション失敗時に入力済みタイトルと日時が維持される。
- 登録成功後に追加フォームの入力値が初期化される。

### REV-SCH-003：日付の上限・下限付近で未処理例外が発生する

- 重要度：**P2（中）**
- 分類：入力境界値、例外処理
- 該当箇所：
  - `research/views.py:334-354`
  - `research/views.py:462-479`

#### 内容

`date` パラメーターは `date.fromisoformat()` で検証されるため、`9999-12-31` や `0001-01-01` は有効な入力として受理される。その後、表示期間や前後ナビゲーションを生成する際に日数を加減するため、Pythonの `date` が扱える範囲を超えて `OverflowError` が発生する。

例：

- `GET /schedule/?view=day&date=9999-12-31`
- `GET /schedule/?view=month&date=9999-12-31`
- `GET /schedule/?view=day&date=0001-01-01`

現状ではこの例外が処理されず、500エラーになる。

#### 影響

- 認証済み利用者が特定のURLを開くとサーバーエラーになる。
- アプリケーションログに不要な例外が記録される。
- 前後移動URLを安全に生成できる日付範囲が定義されていない。

#### 推奨修正

- スケジュールで許可する年の範囲を定義し、範囲外の入力を404または400として処理する。
- または、期間・ナビゲーション計算で発生する `OverflowError` を捕捉し、利用者向けのエラーレスポンスへ変換する。
- 上限・下限では移動リンクを無効化する方法も検討する。

#### 追加すべきテスト

- 年の上限・下限付近の日・週・月表示が500にならない。
- 許可範囲外の日付に対して仕様どおりの404または400を返す。
- 表示可能な境界日で前後移動リンクが安全に生成される。

## 4. 良好だった点

- 表示可能な予定を `_visible_events()` に集約し、本人、共通予定、参加予定を一貫して絞り込んでいる。
- `.distinct()` によって、担当者本人が参加者にも含まれる場合の重複表示を防いでいる。
- 表示期間を `[開始, 終了)` として扱い、日・週・月のクエリ境界が明確である。
- ローカルタイムゾーンを使用して日付境界と表示日を計算している。
- 参加者として追加されただけのユーザーは編集・削除できず、404を返す権限制御が実装されている。
- 終了日時が開始日時より前の場合のフォーム検証が実装されている。
- 月・週・日表示、期間移動、今日の強調、参加者表示について自動テストが用意されている。
- 関連データを `select_related()` と `prefetch_related()` で取得し、テンプレート描画時のN+1クエリを抑えている。
