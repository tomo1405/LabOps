# 下流工程の開発フロー

要件定義・設計が固まった後の「実装 → テスト → リリース → 運用保守」を、毎回抜け漏れなく同じ流れで進めるためのスキル。各工程を省略しない。特にテストの省略は避ける。

## 全体の流れ

1. 実装(Implementation)
2. テスト(Testing)
3. リリース(Release / Deploy)
4. 運用・保守(Operate & Maintain)

## 1. 実装

- 着手前に、対応範囲を一言で要約する。設計や指示が曖昧な場合は、実装方針を短く提案してから着手する(要件・設計そのものが未確定なら、このスキルの範囲外なので先に固めるよう伝える)。
- 既存のコーディング規約・ディレクトリ構成・命名規則に合わせる。新しいスタイルを持ち込まない。
- 小さく分割し、1コミット1目的を意識して実装する。
- 実装中に設計上の矛盾や問題を見つけたら、勝手に解釈して進めず一旦報告する。

## 2. テスト

- 実装した機能に対応するテスト(単体テスト中心)を必ず作成する。既存のテストフレームワーク・命名規則があればそれに従う。
- 正常系だけでなく、エッジケース・異常系も最低限カバーする。
- 実装完了後は必ずテストを実行し、結果を確認してから完了報告する。失敗するテストがあれば原因を修正してから報告する。
- 既存のテストを壊していないか(リグレッション)を確認する。

## 3. リリース

- リリース前チェックリスト:
  - [ ] テストが全て通っている
  - [ ] lint / フォーマッタが通っている
  - [ ] 変更内容のサマリー(コミットメッセージ / PR説明)を用意している
- 破壊的変更がある場合は明示し、影響範囲とマイグレーション手順を記載する。
- 本番環境への反映・mainブランチへのマージなど、実際のデプロイ操作は必ずユーザーの明示的な承認を得てから行う。

## 4. 運用・保守

- 不具合報告や改善要望を受けたら、まず再現手順と影響範囲を確認してから修正に入る。
- 修正は「1. 実装」→「2. テスト」の流れに戻して対応する。
- リファクタリングやパフォーマンス改善などの提案は歓迎するが、必ずユーザーの合意を得てから着手する。

## 注意事項

- このスキルは実装以降の下流工程を担当する。要件定義・設計はプロジェクト側の指示、または人間との事前のすり合わせに従う。
- 各工程の順序(実装→テスト→リリース→運用保守)を飛ばさない。「テストは後でいい」と言われても、最低限のテストは提案する。
